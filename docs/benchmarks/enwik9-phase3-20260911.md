## Scope

This note records the Nereids Phase 3 result on `enwik9`:

- input size: `1,000,000,000` bytes
- input SHA-256:
  `159b85351e5f76e60cbe32e04c677847a9ecba3adc79addab6f4c6c7aa3744bc`

The tested adapter is explicitly DU3-dependent:

```text
DU3 merged.dict + local_u16 + gmap24
→ decode DU lexemes
→ canonical lexeme bytes
→ precomputed DU GID → target-vocabulary ID[] map
→ streamed target-vocabulary IDs
→ exact byte reconstruction
```

The DU3 `merged.dict` serialization contains DU control/magic encodings. Nereids restores each dictionary entry to its canonical byte sequence before target-vocabulary mapping. Those encodings are part of the DU3 serialization contract.

The target vocabulary is the complete mergeable vocabulary of `cl100k_base` from `tiktoken 0.14.0`, exported once to the Nereids `model.bin` format. It is corpus-independent and reusable across DU corpora.

This establishes byte-exact projection from the tested DU3 representation into the full `cl100k_base` mergeable vocabulary.

## Non-claim

This receipt does **not** claim that the emitted Nereids ID sequence equals the canonical `cl100k_base` BPE segmentation produced by `tiktoken.encode()`.

The emitted IDs are valid `cl100k_base` mergeable IDs and reconstruct the exact bytes, but the current Phase 3 adapter greedily factorizes each decoded DU lexeme against the target vocabulary.

Canonical tokenizer segmentation and exact information identity are separate claims.

## Architectural boundary

Current tested path:

```text
bytes
→ DU3 structural representation
→ decoded DU lexeme bytes
→ precomputed target-vocabulary map
→ target-vocabulary IDs
→ exact bytes
```

The structural result supports the working thesis:

> The representation required to preserve information exactly is not identical to the segmentation convention selected by a tokenizer.

Rare1, rengrams, zRank, learned projections, and canonical-tokenizer repair are outside this receipt and are intentionally left for later work.
